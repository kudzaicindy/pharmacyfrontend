CHAPTER 4: RESULTS AND DISCUSSION
This chapter outlines the outcomes of the MediConnect pharmacy connection platform developed as a capstone project at the University of Zimbabwe. It covers hardware and software requirements, the testing strategy and module test cases, implementation details for each system component, and screenshots of the deployed web application. The goal is to demonstrate how the AI-powered pharmacy search platform improves medicine access for patients, supports pharmacists in managing inventory and responses, and gives administrators full visibility over platform operations.

4.3 TESTING STRATEGY
The system was tested using a combination of integration testing and system-level acceptance testing to ensure quality, accuracy, and functional correctness across all three user roles.
4.3.1 TEST OBJECTIVES
Verify that patients can search for medicines, submit requests, and receive ranked pharmacy options via the AI chatbot.
Confirm that prescription image upload correctly extracts medicine names through the Gemini Vision OCR pipeline.
Ensure pharmacists can view requests, submit availability responses, manage inventory, and receive real-time WebSocket notifications.
Validate the MCDA ranking algorithm correctly orders pharmacy responses by price, distance, and availability.
Verify smooth integration between the Django REST backend, Django Channels WebSocket layer, React SPA frontend, and Gemini AI service.

4.5 IMPLEMENTATION OF THE DESIGN (CODING AND SIMULATION)
The implemented MediConnect system consists of five core components that interact cohesively to deliver the pharmacy connection experience. The architecture is designed across two repositories — pharmacybackend (Django REST API) and pharmacyfrontend (React SPA) — with the AI subsystem running entirely on the backend and the PDF export handled client-side. Below is a description of each major component as implemented.
COMPONENT 1: AI CHATBOT AND SYMPTOM GUIDANCE (Chatbot.jsx + chatbot/services.py)
The first component is an AI-powered chatbot that guides patients through medicine discovery. Patients describe their symptoms in natural language through the Chatbot.jsx component, which sends the query to POST /api/chatbot/chat/ on the backend. The chatbot.services module invokes the Google Gemini API via the google-generativeai library to generate contextually relevant medicine suggestions accompanied by a safety advisory. All messages are persisted in ChatConversation and ChatMessage models, and the chatbot_session_id and chatbot_conversation_id stored in the patient&apos;s localStorage are passed as query parameters to maintain multi-turn context. This component directly addresses the patient&apos;s inability to interpret symptoms without clinical guidance.
COMPONENT 2: PRESCRIPTION IMAGE UPLOAD AND OCR (chatbot/services.py + Gemini Vision)
The second component handles the upload and analysis of prescription images. Patients upload a prescription photograph through the patient portal; the backend passes the image through a Pillow and OpenCV preprocessing pipeline before submitting it to the Gemini Vision model via POST /api/chatbot/upload-prescription/. The model extracts medicine names which are injected into the active ChatConversation context, allowing the chatbot to use them in subsequent ranking requests. A session_type field on ChatConversation ensures that prescription metadata is scoped to its session and cannot contaminate a separate symptom-only chat. For low-quality or handwritten prescriptions, a quality_warning flag is returned and displayed to the patient.
COMPONENT 3: MEDICINE REQUEST BROADCAST AND MCDA RANKING (chatbot/services.py)
The third component covers the core request-and-ranking flow. When a patient confirms a medicine request, a MedicineRequest record is created and broadcast in real time to all verified pharmacies in the patient&apos;s area via Django Channels WebSocket. Pharmacists see the request in their PharmacyDashboard.jsx and submit a PharmacyResponse with availability and price. The MCDA ranking engine in chatbot.services scores all responses using price, distance, availability, and verified status as criteria. Where a pharmacy also holds a live PharmacyInventory entry for the requested medicine, it receives a confirmed-stock indicator and ranking boost. The ranked list is returned to the patient via GET /api/chatbot/request/&lt;uuid&gt;/ranked/ for selection.
COMPONENT 4: RESERVATION MANAGEMENT (Reservation model + record_purchase endpoint)
The fourth component manages the reservation lifecycle. Once a patient selects a pharmacy from the ranked listing, a Reservation record is created via POST /api/chatbot/reserve/ with the price_at_reservation field copied from the originating PharmacyResponse — ensuring the quoted price is preserved even if the pharmacy later updates its inventory. The reservation carries a time-bounded pickup window; if the patient does not collect within the window, the reservation expires automatically and the inventory hold is released. On collection, the pharmacist marks the reservation as picked_up, which triggers POST /api/chatbot/record-purchase/ to decrement PharmacyInventory by the reserved quantity. Commercial settlement is handled off-platform (in-store).
COMPONENT 5: ADMIN ANALYTICS, REPORTING, AND GOVERNANCE (admin_analytics.py + AdminDashboard.jsx)
The fifth component covers platform administration. Administrators access aggregated statistics, SLA metrics, and pharmacy verification queues through AdminDashboard.jsx and the AdminControlCenter pages. AI-generated narrative reports are produced by sending aggregate platform data to the Gemini API; the Markdown response is parsed by the marked library in AdminDashboard.jsx and converted to a downloadable themed PDF by jsPDF — entirely client-side, without a server-side PDF renderer. Platform governance features include dynamic chatbot safety settings via PlatformAdminSettings, a ChatbotSafetyReview queue, and a full AdminAuditLog for all mutating admin operations.
4.6 SYSTEM ARCHITECTURE AND INTEGRATION
All five components communicate within a unified interface across two repositories. The pharmacybackend Django project exposes all business logic through the /api/chatbot/ route group in chatbot/urls.py and chatbot/views.py. The pharmacyfrontend React SPA (built with Vite 7) communicates with the backend exclusively through REST calls via the src/utils/api.js module and a Django Channels WebSocket connection. Role-based session management partitions the three user contexts: patients use JWT tokens stored in localStorage (patient, chatbot_session_id, chatbot_conversation_id, token); pharmacists use a parallel localStorage structure (pharmacist, pharmacist_id, pharmacy_id, token); administrators use Django session cookies combined with a CSRF token bootstrapped from /api/chatbot/admin/csrf/ before any mutating request.
The Daphne ASGI server runs pharmacybackend.asgi:application in production, handling both HTTP and WebSocket connections concurrently. The frontend dist/ bundle is deployed to a static host (Vercel or Netlify) with VITE_API_URL set to the backend origin at build time. CORS policy is managed by django-cors-headers. The complete data model comprises: ChatConversation, ChatMessage (AI layer); MedicineRequest, PharmacyResponse, ranking snapshots (request/response layer); Pharmacy, Pharmacist, PharmacyInventory, PharmacyRating (directory layer); PatientProfile, SavedMedicine, PatientNotification, Reservation (patient layer); and PlatformAdminSettings, ChatbotSafetyReview, PharmacySettings, AdminAuditLog (governance layer).
